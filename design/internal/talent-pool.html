“Success” means a draft, not a candidate

Phase 1 extraction pre-fills a form that a human reviews and confirms; nothing enters the database unread. The final button says Review 41 drafts rather than “41 candidates added”, because the second sentence would be false and would train recruiters to skip the step the ADR exists to protect.

Zawgyi is fixed at ingest, silently

A Word file authored in Zawgyi extracts as garbage even with no OCR involved, so normalisation to Unicode happens on the way in and is never a user-facing choice. The one place it surfaces is a review card, when the normalised name differs from the raw bytes and a human should glance at it.

“Review” → the merge nobody should do blind

Two records, one person?

On the public path a phone or email match auto-attaches the new application to the existing candidate — filling blanks, never overwriting. This screen is the other case: two candidates that were already created separately, which the module doc lists as still needing a human confirmation step. Merging is not reversible, so nothing here is automatic.

“Not the same person” is remembered, so the pair stops being flagged.

Three buttons, because there are three real answers

Common Burmese names collide constantly, and a shared family phone is normal here — so “not the same person” is not an edge case, it is the frequent answer. A two-button merge dialog forces a recruiter to either merge two strangers or leave the flag on the list forever, and they will pick whichever gets the badge off their screen.
