No “Sign up” link, and that is the product

Every account here belongs to an employee, and employees are provisioned by an admin on the Users screen. A self-signup link on a system that holds salary bands and rejection reasons would be a defect, so the absence is stated in words rather than left as a missing element the user hunts for.

3 — Rejected

RecruitOps

Email or password is incorrect

The message never says which of the two was wrong — that difference tells a stranger whether an email address is a real employee, and AuthService returns an identical 401 either way for exactly that reason. Only the password field is outlined, because only it is worth retyping.

There is deliberately no “2 attempts remaining” hint: the 401 carries no body, so the page has nothing to count with. Adding the hint means changing the API, and that is a security change, not a copy change.

Why this state does not leak an account

The obvious worry is that “too many attempts” tells a stranger the address is real, undoing the identical-401 the rejected state works so hard for. It does not, because failures are counted for every email, real or not — an invented address locks out exactly the same way. That is a deliberate choice in ADR-0016, asserted by LoginThrottleTests, and the screen inherits it for free.

No “contact your administrator to unlock”. Admin unlock was considered and rejected: any sticky lockout is a griefing weapon — anyone who knows a colleague's email could lock them out at will. 15 minutes, self-clearing, is the whole policy. The screen must not offer an escape hatch the product refuses to build.

The countdown is real rather than decorative: the 429 carries a Retry-After header in seconds.

6 — Reset requested

Didn't arrive? Check spam, then contact your administrator.

“If … belongs to an account” is doing the same work as the rejected state: the page is identical whether or not the address exists, so it cannot be used to enumerate staff.

What is deliberately not on this screen

  • Single sign-on. Module 7.3 covers Microsoft 365 and Google Workspace for calendar and mail. That is not the same as SSO, and no ADR grants it. A “Sign in with Microsoft” button here would be a promise the backend cannot keep.
  • A CAPTCHA, and any “unusual sign-in” notice. ADR-0016 puts both explicitly out of scope for now. Drawing them would misrepresent a decision that was made and written down.
  • Two-factor. Not in any module doc or ADR. Worth raising for a system holding salary bands, but it is a product decision, not something a design page should quietly invent.
  • A workspace / subdomain field. See the note at the top — the deployment is the company.
