Why an old chain is kept

Requisitions approved last year point at its steps. Deleting it would leave those approvals attributed to nothing, so chains deactivate rather than disappear — the same rule as leavers on the Users screen.

This rule has nowhere to live yet

ApprovalChain stores a name, an optional department and an active flag. There is no condition, no amount and no operator. Three screens in this kit already show an approver “added by threshold rule” — the requisition detail, the raise form and the offer approval — so the feature is drawn as if it exists in three places and is stored in none.

Either the entity gains condition fields, or those three screens are wrong. Backend decision, not a design one — it is surfaced here because this is where an admin would look for the switch.

Approve forward, never reject forward

A senior approving on a junior's behalf still lets the requisition proceed — the same outcome the junior's approval would have produced. Rejecting on their behalf ends it before the junior ever sees it. The record names who actually acted whenever it is not the assigned approver (ADR-0024).

A rejection sends it back, it does not kill it

Rejecting ends the round, not the requisition. The raiser revises and resubmits, and a new round starts at step 1 with the previous round's reason still readable (ADR-0023). Chains therefore need no “send back to” target — there is only backwards.

“People scoped” is here on purpose

It is the only place an admin sees department scope as a whole rather than one user at a time. A department with 0 people scoped and 4 open requisitions is a configuration error nobody would otherwise notice.

Renaming is safe, deleting is not offered

Department carries an IsActive flag and no delete path in this design. An inactive department accepts no new requisitions, keeps every old one readable, and stops appearing in the scope picker.
