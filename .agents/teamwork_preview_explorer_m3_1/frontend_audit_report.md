**Scope:** Internal SPA (`frontend/internal`), Public SSR App (`frontend/public`), Shared Workspace Packages (`packages/types`, `packages/ui`), End-to-End User Flows, and 3 Specific UI Gaps (`docs/status/NEXT-SESSION.md`).

## 1. Executive Summary

A comprehensive frontend audit of the RecruitOps platform has been conducted across both applications (`frontend/internal` and `frontend/public`) and shared workspace packages. The frontend architecture cleanly mirrors the backend Clean Architecture and Domain rules.

### Key Audit Conclusions:
1. **Architecture & Monorepo Setup:** The monorepo structure using npm workspaces (`@recruitops/internal`, `@recruitops/public`, `@recruitops/types`, `@recruitops/ui`) operates as intended per ADR-0012. Type definitions and design tokens are centrally maintained, preventing drift between the internal SPA and public SSR application.
2. **End-to-End User Flows:** All 9 internal SPA flows (Login → Requisition → Submit Approval → Approver Inbox → Approve/Reject → Posting Creation → Pipeline Board → Interview Scheduling → Scorecard → Notes) and all 3 public SSR flows (Public job page rendering, dynamic application form rendering, application submission) are fully implemented, role-gated, and aligned with backend contracts.
3. **UI Gap 1 (Panel Picker Role Filtering):** **VERIFIED.** In `ApplicationDebrief.tsx` (lines 487–492), recruiters call `GET /api/users/selectable` (ADR-0019), which returns a list of selectable users (`id`, `displayName`, `role`) without email addresses. Hiring Managers and Approvers are barred from managing scheduling (`canManage = isRecruitmentStaff(role)`), hiding the form and preventing 403 errors.
4. **UI Gap 2 (Blind State Enforcement):** **VERIFIED.** On `/interviews/:id` (`InterviewDetailPage.tsx`), blind scoring (ADR-0017 §3) is enforced server-side and accurately rendered across 3 client states (blinded with `hiddenCount > 0`, blinded with `hiddenCount === 0`, unblinded post-submit or for non-panel recruiters). Non-panel members receive a 404 on draft endpoints and view submitted evaluations read-only without a submission form.
5. **UI Gap 3 (`.mention` CSS Build/Purge):** **VERIFIED.** The `.mention` class is defined in `frontend/internal/src/index.css` as a raw CSS rule outside `@layer` directives. Tailwind CSS v3 preserves raw root CSS rules during production builds without purging them. Mentions are rendered safely via `dangerouslySetInnerHTML` from server-escaped `NoteDto.bodyHtml` (generated by `MentionParser.ToSafeHtml`).

## 2. Codebase Architecture & Structural Audit

### 2.1 Monorepo Workspace Organization
The workspace is configured at the root `package.json`:
```json
"workspaces": [
  "packages/*",
  "frontend/internal",
  "frontend/public"
]
```

- **`packages/types` (`@recruitops/types`):** Contains TypeScript mirrors of backend DTOs and Domain enums (`UserRole`, `PipelineStatus`, `RequisitionStatus`, `ApprovalDecision`, `JobStatus`, `EmploymentType`, `HireRecommendation`, `ScorecardStatus`). Shared functions such as `parseFormFields` provide safe schema parsing.
- **`packages/ui` (`@recruitops/ui`):** Contains shared design system tokens in `tailwind-preset.js` (colors: `primary-700`, `surface-50`, `ink-900`, etc.; fonts: `Inter`, `Noto Sans Myanmar`, `Bricolage Grotesque`) and atomic UI components (`Button`, `Card`, `StatusPill`).

### 2.2 Internal SPA (`frontend/internal`)
- **Technology Stack:** Vite 5.4 + React 18.3 + React Router DOM 6.26 + Tailwind CSS 3.4.
- **Authentication & Storage (`src/lib/auth.ts`):** Sessions are stored in `sessionStorage` under `recruitops.session`. Expired tokens are automatically purged upon retrieval.
- **Role-Based Access Control (`src/lib/auth.ts`):** Client-side role predicates (`isDepartmentScoped`, `isExcludedFromCandidateData`, `isRecruitmentStaff`, `canApprove`, `isAdmin`) mirror `RecruitOps.Domain.RoleScope` in C#.
- **API Client (`src/lib/api.ts`):** Wraps standard `fetch` with relative base URL `/api` (proxied by Vite in dev to `http://localhost:5080`). Intercepts `401 Unauthorized` to clear local session and redirect to `/login`.

### 2.3 Public SSR App (`frontend/public`)
- **Technology Stack:** Next.js 14 App Router (Node 22 runtime) + Tailwind CSS 3.4 + React 18.3.
- **SSR Strategy:** Uses Next.js Server Components for job pages (`/jobs/[token]`) to enable social media Open Graph metadata unfurling (Facebook, Telegram, Viber).
- **Client Component Isolation:** Only `ApplicationForm.tsx` uses `'use client'`, ensuring the rest of the page is server-rendered without hydration overhead.
- **Server API Resolution (`lib/api.ts`):** Dynamically uses `API_INTERNAL_URL` (default `http://localhost:5080/api`) on the server side and relative `/api` in the browser.

## 3. Internal SPA User Flow Verification (End-to-End Walkthrough)

### Flow 1: Login & Session Setup
- **Component:** `LoginPage.tsx` (lines 8–72)
- **Endpoint:** `POST /api/auth/login`
- **Execution:** User submits email and password. Receives `LoginResponse` containing `accessToken`, `expiresAtUtc`, `role`, `displayName`, `userId`. `auth.set()` saves it to `sessionStorage`. On success, navigates to intended path or `/requisitions`.
- **Security Check:** API returns identical generic 401 for wrong password or non-existent email (prevents user enumeration).

### Flow 2: Requisition Creation & Editing
- **Components:** `RequisitionsPage.tsx`, `RequisitionFormPage.tsx`
- **Endpoints:** `GET /api/requisitions`, `GET /api/departments`, `GET /api/jdtemplates`, `POST /api/requisitions`, `PUT /api/requisitions/:id`
- **Execution:** `RequisitionFormPage` handles both `create` and `edit` modes. Departments picker fetches `GET /api/departments` (scoped server-side for Hiring Managers per ADR-0003). Prefills content if a JD template is chosen. Requisition edit (`PUT`) is strictly enforced as Draft-only (returns 409 if status is `PendingApproval`, `Approved`, or `Rejected`).

### Flow 3: Requisition Submission
- **Component:** `RequisitionDetailPage.tsx` (lines 49–50, 181–193)
- **Endpoint:** `POST /api/requisitions/:id/submit`
- **Execution:** Requester clicks "Submit for approval". Backend snapshots the department or company-wide `ApprovalChain` into sequential `ApprovalStep`s and updates requisition status to `PendingApproval`.

### Flow 4: Approver Inbox & Decision (Approve / Reject / Cancel)
- **Components:** `InboxPage.tsx`, `RequisitionDetailPage.tsx`
- **Endpoints:** `GET /api/requisitions/inbox`, `POST /api/requisitions/:id/decision`, `POST /api/requisitions/:id/cancel`
- **Execution:** Approver views `/inbox`. Inbox returns only requisitions where the caller is the named approver for the first `Waiting` step. Approver opens detail page, enters optional comment, and clicks Approve or Reject. Requester or Admin/HrDirector can also withdraw/cancel at any pre-decision state.

### Flow 5: Posting Creation & Publishing
- **Components:** `JobPostingsPage.tsx`, `JobPostingDetailPage.tsx`, `FormFieldBuilder.tsx`
- **Endpoints:** `GET /api/jobpostings`, `POST /api/jobpostings`, `PUT /api/jobpostings/:id`, `POST /api/jobpostings/:id/publish`, `POST /api/jobpostings/:id/close`
- **Execution:** `JobPostingsPage` queries approved requisitions missing postings. Recruiter creates posting (`POST /api/jobpostings`), edits details, builds custom application form fields (`FormFieldBuilder`), and publishes. Publishing generates an unguessable `publicToken` and shareable URL (`http://localhost:3000/jobs/[publicToken]`).

### Flow 6: Pipeline Board & Stage Movement
- **Component:** `JobPostingDetailPage.tsx` (lines 303–388)
- **Endpoints:** `GET /api/jobpostings/:id/pipeline`, `POST /api/applications/:id/stage`
- **Execution:** Renders pipeline candidates across 8 stages (`Sourced`, `Applied`, `Screening`, `Shortlisted`, `Interview`, `Offer`, `Hired`, `Rejected`). Custom question answers are displayed using `CustomAnswers` component. Moving a candidate stage calls `POST /api/applications/:id/stage`, which appends an `ApplicationStageHistory` row. Terminal stages (`Hired`, `Rejected`) disable further stage moves.

### Flow 7: Interview Scheduling & Panel Assignment
- **Component:** `ApplicationDebrief.tsx` (lines 163–262, 460–581)
- **Endpoints:** `GET /api/applications/:id/interviews`, `POST /api/applications/:id/interviews`, `GET /api/users/selectable`
- **Execution:** Recruiter clicks "Schedule interview" under candidate debrief. Form loads selectable users via `GET /api/users/selectable`. Recruiter selects panel members (`participantUserIds`) and optional lead (`leadUserId`). Scheduling automatically transitions candidate to `Interview` stage and logs stage history in a single transaction.

### Flow 8: Scorecard Evaluation, Draft Saving & Blind Enforcement
- **Components:** `InterviewDetailPage.tsx`, `src/lib/scorecard.ts`
- **Endpoints:** `GET /api/interviews/:id`, `GET /api/interviews/:id/scorecards`, `GET /api/interviews/:id/scorecard`, `PUT /api/interviews/:id/scorecard`, `POST /api/interviews/:id/scorecard/submit`
- **Execution:** Panel member opens `/interviews/:id`. Form loads criteria and candidate evaluation. Draft saving (`PUT`) omits untouched criteria (`isSendable` in `scorecard.ts`) to avoid backend validation failure on `null` ratings. Submitting (`POST .../submit`) requires all mandatory criteria answered and an overall recommendation. Server enforces blind scoring: until submitted, other panel evaluations remain hidden.

### Flow 9: Debrief Notes & @Mentions
- **Components:** `ApplicationNotes.tsx`, `ApplicationNotes.test.tsx`
- **Endpoints:** `GET /api/applications/:id/notes`, `POST /api/applications/:id/notes`
- **Execution:** Users post notes with `@handle` references. Server parses handles via `MentionParser.ToSafeHtml`, resolves mentions against users authorized to access the application (ADR-0018), and returns safe `bodyHtml`. Rendered using `dangerouslySetInnerHTML` in `NoteBody`.

## 4. Public SSR App User Flow Verification

### Flow 1: Public Job Page Rendering & Open Graph Metadata
- **File:** `frontend/public/app/jobs/[token]/page.tsx`
- **Execution:** Next.js Server Component fetches job details via `GET /api/public/jobs/:token`. Returns 404 for invalid/expired/closed tokens.
- **Open Graph Metadata:** `generateMetadata` constructs dynamic meta tags:
  ```typescript
  return {
    title: `${job.title} — ${job.companyName}`,
    description: summarize(job.description, 200),
    openGraph: { title, description, type: 'website', siteName: job.companyName },
    twitter: { card: 'summary_large_image', title, description },
    robots: { index: false, follow: false },
  };
  ```

### Flow 2: Dynamic Custom Application Form Rendering & Validation
- **File:** `frontend/public/app/jobs/[token]/ApplicationForm.tsx`
- **Execution:** Client Component parses `applicationFormFieldsJson` via `parseFormFields`. Renders default candidate fields (`fullName`, `email`, `phone`, `coverNote`) plus custom inputs (`text`, `textarea`, `number`, `date`, `select`, `checkbox`). Ensures at least one contact method (email or phone) is provided before sending.

### Flow 3: Application Submission & Backend Sync
- **Endpoint:** `POST /api/public/jobs/:token/apply`
- **Execution:** Sends applicant details and JSON-serialized custom answers. Backend `PublicJobService` verifies token, ignores tenant query filters, re-applies tenant from job row, normalizes contact details for deduping, creates `Candidate` and `JobApplication`, and logs initial `ApplicationStageHistory` row. Form renders confirmation message upon completion.

## 5. Deep-Dive Audit of the 3 Specific UI Gaps (`NEXT-SESSION.md`)

### 5.1 UI Gap 1: Panel Picker Population by Recruiter Role vs Other Roles (ADR-0019)
- **Context:** Recruiter role needed to select interview panel members, but `GET /api/users` was restricted to `AdminOnly`. ADR-0019 introduced `GET /api/users/selectable` for `RecruitmentStaff`.
- **Code Inspection (`ApplicationDebrief.tsx` lines 467–492):**
  ```typescript
  const role = auth.get()?.role;
  const canManage = role ? isRecruitmentStaff(role) : false;
  
  useEffect(() => {
    if (!canManage) return;
    api<SelectableUser[]>('/users/selectable')
      .then(setUsers)
      .catch(() => setUsers([]));
  }, [canManage]);
  ```
- **Findings:**
  1. **Recruiter Role:** `isRecruitmentStaff('Recruiter')` is `true`. `canManage` evaluates to `true`. `useEffect` triggers `GET /api/users/selectable`, successfully fetching user list and populating `PanelPicker`.
  2. **HiringManager / Approver Roles:** `isRecruitmentStaff` returns `false`. `canManage` is `false`. The API fetch is skipped, scheduling forms are hidden, and if invoked directly, backend rejects with 403.
  3. **Data Protection:** `SelectableUser` contains `id`, `displayName`, and `role` only — no email address is returned or exposed.
- **Verdict:** **VERIFIED & FUNCTIONAL.**

### 5.2 UI Gap 2: Blind State Enforcement on Interview Details View (`/interviews/:id`)
- **Context:** ADR-0017 §3 requires panel scorecards to remain blind until the user submits their own scorecard.
- **Code Inspection (`InterviewDetailPage.tsx` lines 388–418):**
  ```typescript
  {panel.blindedUntilYouSubmit && panel.hiddenCount > 0 && (
    <p className="mb-4 rounded-sm bg-warning-100 p-3 text-[15px] text-warning-600">
      {panel.hiddenCount} {panel.hiddenCount === 1 ? 'evaluation is' : 'evaluations are'}{' '}
      waiting for yours. They unlock as soon as you submit…
    </p>
  )}
  {panel.blindedUntilYouSubmit && panel.hiddenCount === 0 && (
    <p className="mb-4 text-[15px] text-ink-600">
      Nobody else has submitted yet. Their evaluations will appear here once you have submitted yours.
    </p>
  )}
  ```
- **Findings:**
  1. **Blinded State (Unsubmitted):** If `blindedUntilYouSubmit` is `true` and `hiddenCount > 0`, warning banner displays exact hidden count without revealing scores or comments.
  2. **Blinded State (Zero Submissions):** If `hiddenCount === 0`, clear feedback informs user that nobody else has submitted.
  3. **Unblinded State (Post-Submit / Non-Panel Recruiter):** `panel.visible` lists all submitted scorecards (`ScorecardView`).
  4. **Non-Participant View:** When viewed by a recruiter not on panel, `GET /api/interviews/:id/scorecard` returns 404. Handled cleanly with `setMine(null)`. Form is omitted (`Your evaluation` card hidden) while read-only scorecards are displayed.
- **Verdict:** **VERIFIED & FUNCTIONAL.**

### 5.3 UI Gap 3: `.mention` CSS Class Build/Purge Survival & Design Alignment
- **Context:** Mentions in notes are rendered as `<span class="mention" data-user-id="...">@DisplayName</span>`. The markup is generated server-side in C#, so Tailwind content scanners cannot find class references in TSX files.
- **Code Inspection:**
  - `frontend/internal/src/index.css` (lines 25–31):
    ```css
    .mention {
      font-weight: 600;
      color: theme('colors.primary.700');
      background: theme('colors.primary.100');
      border-radius: 3px;
      padding: 0 2px;
    }
    ```
  - `frontend/internal/tailwind.config.js` (lines 4–8):
    ```javascript
    export default {
      presets: [preset],
      content: ['./index.html', './src/**/*.{ts,tsx}', '../../packages/ui/src/**/*.{ts,tsx}'],
    };
    ```
- **Findings:**
  1. **Purge Behavior:** In Tailwind v3, CSS rules defined at the root of `index.css` (outside `@layer` blocks) are treated as custom plain CSS and passed through to the build output without purging.
  2. **HTML Injection Safety:** `ApplicationNotes.tsx` uses `dangerouslySetInnerHTML={{ __html: html }}` to render `NoteDto.bodyHtml`. Server-side `MentionParser.ToSafeHtml` escapes all user input before injecting `<span class="mention">`.
  3. **Unit Test Verification:** Tested in `ApplicationNotes.test.tsx` (lines 30–44), asserting `container.querySelector('span.mention')` is present and valid.
- **Verdict:** **VERIFIED & FUNCTIONAL.**
